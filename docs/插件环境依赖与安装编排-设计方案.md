## 一、目标、非目标、验收口径

### 1.1 目标

1. 插件包可**声明式**描述环境：Python 包、系统包、外部客户端、systemd 服务、端口
2. 安装时**先检查**，产出结构化报告：缺什么、为什么缺、能否自动补、怎么手动补
3. 能自动的自动做（venv + pip / apt / unit 落盘），不能自动的**诚实转人工引导**
4. 市场安装与上传安装**共用同一个检查与执行引擎**，只是呈现不同
5. 端口冲突在**落盘前**发现，并区分"本插件自己占的"（升级场景）与"别人占的"
6. 全程向后兼容，面板版本号不变

### 1.2 非目标

- 不做依赖求解器（不处理版本回溯、不生成锁文件）
- 不替第三方客户端做无人值守安装（QQ 扫码无法自动化）
- 不做容器隔离（插件仍在宿主机进程跑，这是现有架构前提）
- 不改 supervisor 的进程拉起逻辑
- 不引入新的包管理器抽象层（apt/dnf/pacman 分支交给 shell，见 §4.6）

### 1.3 验收口径

一个插件算"装好了"，当且仅当：

```
文件已落盘  AND  EnvReport.Ready == true
```

`Ready == false` 时，UI **不允许**显示"安装成功"，必须显示"还需 N 步"。

## 二、现状（代码实测）

### 2.1 `requirements` 声明了但没人装

| 位置 | 事实 |
|---|---|
| `interface/schema/plugin.json.v4.schema.json:16` | 注释声称"安装插件时由面板 pip install" |
| `internal/supervisor/supervisor.go:49-82` | 唯一消费点，**只检查 + `log.Printf`**，不安装；且在启动时查、每进程一次（`depsChecked`） |
| `install.sh:654` | 注释说"装依赖时面板会提示"——提示只在 journalctl，网页看不到 |
| `install.sh:30` | 明确划界："**不含插件**：插件在面板【插件】页安装；插件依赖由各插件自行处理" |

**"自行处理"目前没有任何机制可用。** 这是本次要补的洞。

### 2.2 两条安装链路都不管环境

| | 市场安装 | 面板内直接安装 |

### 2.4 清单表达不了分层依赖

`ManifestV4`（`internal/pluginx/pluginx.go:46`）字段为

## 三、总体设计

### 3.1 三层职责

```
┌─────────────────────────────────────────────────────────────┐
│ 清单层  plugin.json → environment{level, check[], apply[]}   │
│         作者写：检查什么、怎么补。命令是 shell。              │
└───────────────────────────┬─────────────────────────────────┘
                            │ 解析
┌───────────────────────────▼─────────────────────────────────┐
│ 引擎层  internal/pluginrt                                    │
│  · LoadEnvSpec   解析 + 校验（路径穿越/端口范围/必填）        │
│  · Check         只读，产出 EnvReport                         │
│  · Apply         按序执行，产出 []StepResult                  │
│  · checkPort     Go 实现（root 下 ss 能看 PID，比 sh 稳）     │
└───────────────────────────┬─────────────────────────────────┘
                            │ 调用
┌───────────────────────────▼─────────────────────────────────┐
│ 接入层  市场 store.go / 上传 storeupload.go / HTTP / 前端     │
│  · 市场：插进 TaskStore 进度阶段，失败带具体项               │
│  · 上传：同步返回，响应体加 env 字段                          │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 执行顺序（关键：预检前置）

**市场安装**

```
 5%  下载 zipball
15%  解压提取
25%  解析清单 + 环境预检（只读）      ← 新增；不过则中止，不留半装
30%  停旧进程（升级场景）
35%  落盘 + 重扫
40%  环境准备（仅 level=apply 且用户确认） ← 新增
95%  启动 + verify
100% 完成（附 EnvReport 摘要）
```

**上传安装**（保持同步）

```
接收 → InstallFromPackage（现有）→ 重扫 → Check（只读）→ 返回 {ok, env:{...}}
```

上传路径**不自动 apply**：文件装完即返回，`env.pending>0` 由前端引导用户点。

### 3.3 状态机

```
                 ┌──────────┐
   安装请求 ───▶ │ precheck │
                 └────┬─────┘
            Ready=true│        │Ready=false 且 level=check
                      ▼        ▼
                  ┌──────┐  ┌──────────┐
                  │ done │  │ pending  │──用户点「一键修复」──┐
                  └──────┘  └──────────┘                     │
                                     ▲                      ▼
                                     └────── 仍有 missing ──┐
                                                            │
                      level=apply 且确认 ──▶ apply ──▶ verify ──▶ done
```

## 四、清单规范 v4.1

### 4.1 根节点新增字段

在 `interface/schema/plugin.json.v4.schema.json` 的 `properties` 加 `environment`
（**不加入 `required`**，`additionalProperties:false` 保持不变）：

```json
"environment": {
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "level": { "enum": ["check", "apply"], "default": "check" },
    "check": { "type": "array", "items": { "$ref": "#/definitions/checkDef" } },
    "apply": { "type": "array", "items": { "$ref": "#/definitions/applyDef" } }
  }
}
```

完整定义见附录 A。

### 4.2 字段语义

**`level`**

| 值 | 含义 |
|---|---|
| `check`（默认） | 只跑 `check[]`，一个字节都不改。`apply[]` 被忽略（报告里注明"作者声明了 apply 但 level=check"） |
| `apply` | 允许跑 `apply[]`，但市场路径仍需用户确认；上传路径不自动跑 |

**`check[]` 每一项**

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 唯一标识，`^[a-z0-9][a-z0-9_.-]*$`，用于前端定位与 apply 关联 |
| `label` | | 展示名，缺省用 `id` |
| `type` | | `""`（默认，shell）或 `port` |
| `run` | type=shell 时必填 | 交给 `/bin/sh -c`，cwd = 插件目录 |
| `expect` | | 对 stdout 的正则；缺省只看退出码 |
| `port` / `bind` | type=port 时必填 | `bind` 缺省 `127.0.0.1` |
| `owner` | | `{unit:"rcbot.service"}` 或 `{plugin:"self"}`，用于判定"自己占的" |
| `required` | | 默认 `true`；`false` 时失败只降级 |
| `hint` | | 缺失时的一句话说明 |
| `guide` | | 人工引导链接 |
| `timeout` | | 秒，默认 30 |

**`apply[]` 每一项**

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 建议与对应 check 的 id 一致，用于幂等跳过 |
| `label` | | 展示名 |
| `run` | ✅ | 同 `check.run` |
| `needs` | | `auto`（默认，直接跑）/ `root`（非 root 时不执行，只展示命令） |
| `timeout` | | 秒，默认 120；`apt` 类建议显式写 600 |
| `check` | | 关联的 check id；该 check 已 ok 则跳过本步（幂等） |

### 4.3 为什么 `check` 有两种形态

99% 的检查是"跑个命令看退出码"。唯一例外是**端口**：

- 写对的 shell 版本约 25 行（要处理 `ss` 输出格式、root 才能看到别人 PID、`systemctl show MainPID` 比对）
- 每个作者抄一遍必错，且错法是"永远报冲突"（升级时自己占着）

所以端口做成结构化字段，Go 里实现一次。**其余一律 shell，不提供更多类型**——
一旦开始给 check 加 `type: http`、`type: file`，就是在重造 shell。

### 4.4 完整示例（QQBot）

```jsonc
{
  "name": "QQBot",
  "version": "1.1.1",
  "requirements": [],
  "environment": {
    "level": "apply",
    "check": [
      { "id": "napcat", "label": "NapCat 协议端", "required": true,
        "run": "curl -fsS -m 2 -o /dev/null -w '%{http_code}' http://127.0.0.1:6099/webui/",
        "expect": "^2", "hint": "NapCat 未运行或未安装",
        "guide": "https://napcat.napneko.icu/guide/start" },

      { "id": "port6710", "label": "rcbot HTTP 端口", "type": "port",
        "port": 6710, "bind": "127.0.0.1",
        "owner": { "unit": "rcbot.service" }, "required": true },

      { "id": "deps", "label": "rcbot Python 依赖",
        "run": "/opt/rcbot/venv/bin/python -c 'import aiohttp, aiosqlite, PIL'",
        "required": true, "hint": "rcbot 的 venv 缺依赖" },

      { "id": "unit", "label": "rcbot 服务",
        "run": "systemctl is-active --quiet rcbot", "required": true }
    ],
    "apply": [
      { "id": "deps", "label": "建 venv 并装依赖", "needs": "auto", "timeout": 300,
        "run": "python3 -m venv /opt/rcbot/venv && /opt/rcbot/venv/bin/pip install -q 'aiohttp>=3.11' 'aiosqlite>=0.17' 'pillow>=9.0'" },

      { "id": "unit", "label": "注册并启动 rcbot", "needs": "root",
        "run": "install -m0644 service/rcbot.service /etc/systemd/system/ && systemctl daemon-reload && systemctl enable --now rcbot" }
    ]
  }
}
```

> 注意 QQBot 的插件后端本身**零三方依赖**，所以没有 `scope=panel` 的 pip 项。
> 同一份清单里，插件后端不需要包、伴生服务需要三个——这正是今天
> `"requirements": []` 表达不了的东西。

### 4.5 校验规则（解析期就拒绝）

| 规则 | 失败信息 |
|---|---|
| `id` 重复 | `environment.check 中 id 重复: xxx` |
| `type=shell` 但 `run` 为空 | `检查项 xxx 缺少 run` |
| `type=port` 但 `port` ∉ [1024,65535] | `检查项 xxx 端口非法` |
| `run` 里引用的 `from` 路径越出插件目录 | `脚本路径越界: ../../etc/passwd` |
| `apply[].run` 含 `sudo` | 警告（不阻断）：面板是 root 时无需 sudo，非 root 时 sudo 会卡在密码提示 |
| `level=apply` 但 `apply[]` 为空 | 降级为 `check` 并注明 |

**清单非法时不影响插件安装**：环境块被丢弃，`EnvReport` 返回 `{ready:true, items:[], warn:"清单 environment 非法: ..."}`。
理由：环境是增强，不该让一个写错的环境块把能用的插件卡死。

### 4.6 发行版差异交给 shell，不进框架

`install.sh:622-650` 的做法是：apt 系自动装，非 apt 系**打印等价命令**而不是硬失败。

插件侧同理。作者若要跨发行版，自己写：

```sh
command -v apt-get >/dev/null && apt-get install -y xvfb || echo "请手动安装 xvfb"
```

框架不提供 `packages.apt` / `packages.dnf` 这种抽象——它会把作者锁死在
"框架支持的包管理器"里，而 `install.sh:597` 列的六个坑说明这类抽象很难做对。

## 五、Go 数据结构

### 5.1 清单扩展（`internal/pluginx/pluginx.go`）

```go
// ManifestV4 增加一个可选字段。
// json.Unmarshal 忽略未知字段，所以老面板读新包不受影响（见 §12.1）。
type ManifestV4 struct {
    // ... 现有字段不动 ...
    Environment *EnvironmentSpec `json:"environment,omitempty"`
}

type EnvironmentSpec struct {
    Level string     `json:"level,omitempty"` // check|apply
    Check []CheckDef `json:"check,omitempty"`
    Apply []ApplyDef `json:"apply,omitempty"`
}

type CheckDef struct {
    ID       string `json:"id"`
    Label    string `json:"label,omitempty"`
    Type     string `json:"type,omitempty"` // ""|port
    Run      string `json:"run,omitempty"`
    Expect   string `json:"expect,omitempty"`
    Port     int    `json:"port,omitempty"`
    Bind     string `json:"bind,omitempty"`
    Owner    *Owner `json:"owner,omitempty"`
    Required *bool  `json:"required,omitempty"`
    Hint     string `json:"hint,omitempty"`
    Guide    string `json:"guide,omitempty"`
    Timeout  int    `json:"timeout,omitempty"`
}

type Owner struct {
    Unit   string `json:"unit,omitempty"`   // 比对该 systemd 单元的 MainPID
    Plugin string `json:"plugin,omitempty"` // "self" = 本插件进程
}

type ApplyDef struct {
    ID      string `json:"id"`
    Label   string `json:"label,omitempty"`
    Run     string `json:"run"`
    Needs   string `json:"needs,omitempty"` // auto|root
    Timeout int    `json:"timeout,omitempty"`
    Check   string `json:"check,omitempty"`
}
```

`Required` 用 `*bool` 而非 `bool`，才能区分"没写"（默认 true）与"明确写 false"。

### 5.2 报告结构（`internal/pluginrt/envspec.go` 新建）

```go
type CheckItem struct {
    ID       string `json:"id"`
    Label    string `json:"label"`
    Kind     string `json:"kind"`   // shell|port|requirements
    Status   string `json:"status"` // ok|missing|degraded|manual|unknown
    Detail   string `json:"detail,omitempty"` // 输出尾部，≤500 字
    Hint     string `json:"hint,omitempty"`
    Guide    string `json:"guide,omitempty"`
    Fix      string `json:"fix"`    // auto|root|manual|none
    Required bool   `json:"required"`
}

type EnvReport struct {
    Plugin    string      `json:"plugin"`
    Version   string      `json:"version"`
    Level     string      `json:"level"`
    Ready     bool        `json:"ready"`
    Items     []CheckItem `json:"items"`
    Pending   int         `json:"pending"`   // missing 且 required 的数量
    Root      bool        `json:"root"`      // 面板进程 euid==0
    OS        string      `json:"os"`
    Arch      string      `json:"arch"`
    Warn      string      `json:"warn,omitempty"` // 清单非法等
    CheckedAt int64       `json:"checked_at"`
}

type StepResult struct {
    ID     string `json:"id"`
    Label  string `json:"label"`
    OK     bool   `json:"ok"`
    Skipped bool  `json:"skipped,omitempty"` // check 已 ok 而跳过
    Output string `json:"output,omitempty"`  // 截断 4KB
    Err    string `json:"err,omitempty"`
    MS     int64  `json:"ms"`
}
```

### 5.3 执行器

```go
type EnvRunner struct {
    Dir     string   // 插件目录；工作目录 + 脚本基准
    Python  string   // 面板侧解释器（requirements 翻译用）
    SelfPID int      // 本插件进程 PID（owner.plugin=self 用），0=未运行
    Root    bool
    Extra   []string // 追加环境变量，如 RC_PLUGIN_PID=...
}

func (r *EnvRunner) Report(spec *EnvironmentSpec) EnvReport
func (r *EnvRunner) Apply(spec *EnvironmentSpec, ids []string,
    onStep func(StepResult)) []StepResult
```

`onStep` 让市场路径能把每步写进 `TaskStore.Update(id, phase, progress, msg)`，
上传路径传 `nil` 即可。

## 六、检查引擎

### 6.1 流程

```
Report(spec)
  ├─ spec == nil            → {Ready:true, Items:[]}   立即返回
  ├─ 逐条 check[i]
  │    ├─ type=port   → checkPort()
  │    └─ 其他        → runShell()
  ├─ 兼容：清单只有 requirements 且无 environment
  │    → 翻译成 N 条 python import 检查（见 §6.4）
  ├─ Fix 推导（见 6.3）
  └─ Ready = 所有 required 项 Status ∈ {ok}
```

### 6.2 runShell

```go
ctx, cancel := context.WithTimeout(context.Background(), timeout)
cmd := exec.CommandContext(ctx, "/bin/sh", "-c", def.Run)
cmd.Dir = r.Dir
cmd.Env = append(os.Environ(), r.Extra...)
out, err := cmd.CombinedOutput()
```

判定：

| 情况 | Status |
|---|---|
| `err == nil` 且 `expect` 为空 | `ok` |
| `err == nil` 且 stdout 匹配 `expect` | `ok` |
| `err == nil` 但 stdout 不匹配 | `missing`（Detail 带实际输出） |
| `exec.ExitError` | `missing` |
| `ctx.DeadlineExceeded` | `unknown`（不是 missing——超时可能是环境慢） |

`CombinedOutput` 而非 `Output`：作者常把诊断信息打到 stderr，合并后 `Detail` 才有内容。

### 6.3 端口检查（Go 实现，逻辑移植自 `install.sh:68-88`）

```go
func checkPort(def CheckDef, selfPID int, root bool) CheckItem
```

算法：

```
1. ln, err := net.Listen("tcp", joinhostport(bind, port))
   err == nil → ln.Close() → ok（"端口空闲"）
2. 占用：找出 holder PID
   out := exec `ss -ltnp` （root 下才有 pid= 字段；非 root 时退化为无 PID）
   解析 "pid=1234" 取第一个
3. 若 def.Owner != nil：
   a. Owner.Unit != ""：
      main := exec `systemctl show -p MainPID --value <unit>`
      main != "" && main != "0" && main == holderPID → ok（"由本插件依赖的服务占用"）
   b. Owner.Plugin == "self"：
      selfPID > 0 && holderPID == selfPID → ok（"由本插件当前进程占用，升级场景"）
4. 其余 → missing，Detail 写占用进程名（readlink /proc/<pid>/comm）
```

**为什么不在 shell 里做**：`ss` 输出解析 + root 权限陷阱 + MainPID 比对，
`install.sh` 用了 20 行才写对，且注释明确写了"非 root 下看不到别人进程的 PID"。
Go 里 `os.Geteuid()==0` 是确定的，比 sh 里靠 `$SUDO` 猜可靠。

### 6.4 `requirements` 兼容翻译

清单没有 `environment` 但有 `requirements` 时，翻译成检查项（**只检查不安装**，
与今天行为一致，避免升级后突然开始装包）：

```
"requirements": ["jmcomic>=2.7", "requests>=2.31"]
  ↓ 复用 pluginrt.CheckPythonModules(python, reqs) 的剥离逻辑
check: python -c "import jmcomic, requests"
  ↓ 缺失时
CheckItem{ID:"requirements.jmcomic", Fix:"auto", Hint:"python3 -m pip install jmcomic>=2.7"}
```

同时 `env.Warn` 注明："该插件使用旧式 requirements 声明，`Fix` 需手动执行或作者改用 environment"。

### 6.5 超时与并发

- 单条超时：`def.Timeout` 或默认 30s
- 整个 Report 总超时：120s（超过则剩余项标 `unknown`，不阻塞安装）
- **串行执行**，不并发：检查项可能有依赖关系（端口检查依赖服务先起），并发会误报。
  串行的代价可接受——典型插件 3-5 条检查，每条 <1s。

## 七、执行引擎

### 7.1 Step 生成

```
Apply(spec, ids)
  ├─ level != apply → 直接返回 [{Err:"level=check，拒绝执行"}]
  ├─ 选定待执行集合：
  │    ids 非空 → 只跑这些（顺序仍按 apply[] 声明顺序）
  │    ids 为空 → 跑全部
  ├─ 逐条：
  │    ├─ 若 def.Check != "" 且该 check 当前 ok → 跳过（Skipped=true）
  │    ├─ 若 def.Needs == "root" 且 !r.Root → 不执行，Err="需要 root"，Fix 降 manual
  │    ├─ 执行（cwd=插件目录，超时 def.Timeout 或 120s）
  │    └─ onStep(result)
  └─ 失败即停（见 7.4）
```

### 7.2 顺序

**严格按 `apply[]` 声明顺序，不自动重排。**

v1 曾硬定 `pip → apt → systemd → script`，但 QQBot 的真实顺序是
`venv → pip → unit`——先建 venv 才有 pip。作者比框架清楚依赖关系。

### 7.3 输出与审计

- `StepResult.Output` 保留尾部 4KB（诊断信息通常在后半）
- 每次 Apply 结束后 `log.Printf` 一行摘要：
  `[env] QQBot apply: deps=ok(1203ms) unit=ok(310ms)` 
- 完整输出随 `StepResult` 返回前端，同时市场路径写进 `Task.Meta["env"]`

不新增独立审计文件——`journalctl -u raincough` 已能追溯，多一份文件反而没人看。

### 7.4 失败处理

| 情况 | 行为 |
|---|---|
| 某步失败 | **立即停止**后续步骤，返回已完成部分 |
| 停止后 | 重新跑一次 `Report()`，前端拿最新状态（可能部分项已改善） |
| 环境回滚 | **不做**。环境是共享的（JMComic 与 QQBot 可能共用 python），回滚会砸别人 |
| 文件回滚 | 由现有 `replaceDir` 负责，与环境解耦 |

## 八、安全与权限

### 8.1 先承认事实

`plugin.json` 的 `backend.exec` 是 `["python3","server_v4.py"]`，supervisor 直接 fork。
**插件装完就跑任意代码，权限等于面板进程权限**（root 时就是 root）。

所以"安装脚本能跑 shell"**没有扩大攻击面**，只是把同一个信任关系提前到安装时刻。

v1 设计的"脚本 sha256 + 三重校验"是自欺欺人：攻击者能改脚本，当然也能改清单里的
sha256。**已删除。**

### 8.2 保留的三件事

1. **看见要执行什么**
   安装确认页原文展示 `apply[]` 每一条 `run`，不折叠、不省略。
   这比任何签名机制都有效——用户能看出 `rm -rf /` 不对劲。

2. **`level` 默认 `check`**
   不是为了防恶意，是为了防**作者写错**。安装脚本误删目录比恶意代码常见得多。

3. **审计**
   命令原文 + 退出码 + 输出尾部进 journal 与 `Task.Meta`。

### 8.3 硬约束（实现时不可妥协）

| 约束 | 实现 |
|---|---|
| `apply.run` 的工作目录锁定插件目录 | `cmd.Dir = r.Dir` |
| 不接受 `additionalProperties` 之外的结构 | 结构化字段全在 schema 内 |
| 非 root 时不执行 `needs:root` | `if def.Needs=="root" && !r.Root { skip }` |
| 不 `sudo` 提权 | 全仓不出现 `sudo` 调用 |
| 端口只接受 1024-65535 | 解析期校验 |
| 清单非法不阻断安装 | 丢弃 environment，`Warn` 提示 |

> 注：v2 曾有"`from` 脚本路径不得越界"一条。v3 取消了 `from` 字段——
> `run` 里写相对路径本身就是相对 `cmd.Dir`，越界到包外是作者自己写的路径，
> 拦不住也没必要拦（他完全可以写绝对路径）。**约束要拦得住才有意义。**

### 8.4 权限判定

```go
root := os.Geteuid() == 0
```

只判一次，写进 `EnvReport.Root`。前端据此决定：

- `Root=true`：`needs:root` 的步骤显示"一键执行"
- `Root=false`：显示命令原文 + 提示"面板以非 root 运行，请自行执行"

**不猜、不提权、不降级重试。**

## 九、两条安装链路改造

### 9.1 市场安装（`internal/core/store.go:288`）

现状进度 20/50/100。改造后：

```go
func (s *Store) InstallPlugin(name string, task *TaskStore) (string, error) {
    // ... 现有 gtDownload ...
    task.Update(tid, "", 15, "解压...")
    // 解到临时目录后、replaceDir 之前：
    spec := pluginrt.LoadEnvSpec(root)
    rep := (&pluginrt.EnvRunner{Dir: root, Root: isRoot(), ...}).Report(spec)
    if !rep.Ready && firstBlocking(rep) != nil {
        // 只有端口被外人占用这类"硬冲突"才中止
        task.Finish(tid, false, "", "端口冲突: 6710 被 xxx 占用", 0)
        return
    }
    task.Update(tid, "", 30, fmt.Sprintf("环境预检：%d 项待处理", rep.Pending))
    // ... replaceDir ...
    // level=apply 且调用方确认时：
    results := runner.Apply(spec, nil, func(r StepResult){ task.Update(...) })
}
```

**只对"硬冲突"中止**（端口被其他进程占）。缺依赖、缺 NapCat 这类不中止——
装上去至少列表里能看到，用户还能看到缺什么。中止反而让他无从下手。

`Store` 需要新增字段 `EnvApply func(name string) ([]StepResult, error)` 由宿主注入，
与现有 `onInstalled` / `onBeforeRemove` 同模式，避免 `core` 反向依赖 `pluginrt` 的 runner 细节。

### 9.2 上传安装（`cmd/raincough/storeupload.go:35`）

`InstallFromPackage` **完全不动**（它已负责解压/校验/原子替换/回滚）。
只在 handler 里，`Reload`/`Rescan` 之后追加：

```go
rep := envRunner(s.cfg.PluginsDir, info.Name).Report(spec)
writeJSON(w, 200, map[string]interface{}{
    // ... 现有字段 ...
    "env": rep,
    "message": chooseMessage(info, rep), // Ready 与否决定文案
})
```

`chooseMessage`：

```go
if rep.Ready   → "已安装 QQBot v1.1.1（5 个文件），环境就绪"
else           → "已安装 QQBot v1.1.1，还需 2 步才能使用"
```

### 9.3 卸载

`RemovePlugin` 现有逻辑不变。追加：从 `apply[]` 里提取含
`/etc/systemd/system/` 的路径，在卸载响应里列出：

```json
{ "ok": true, "residue": ["/etc/systemd/system/rcbot.service"] }
```

**不自动删 unit**——用户可能改过，删掉比留下危险。

## 十、HTTP API 契约

两个新接口，都挂在现有 `/api/plugins/` 总入口的分发里
（`cmd/raincough/main.go:513` 的 `switch`）：

```go

    s.handlePluginEnvReport(w, r, name)
case sub == "environment/apply" && r.Method == http.MethodPost:
```

## 十一、前端改造与安装浮窗

> 浮窗是这套方案的主交互。环境检查若只放在插件列表里，用户装完还是不知道要干什么；
> **必须有一个"装完就地告诉他差什么、能一键补"的浮层**。

### 11.1 三态一组件

`InstallDock.vue` 一个组件，三种形态按状态自动切换：

| 形态 | 触发 | 尺寸 | 交互 |
|---|---|---|---|
| **胶囊**（mini） | 有任务在跑 / 刚完成 | 56×56 圆球，右下角 | 显示环形进度或绿色对勾；点击展开 |
| **浮窗**（panel） | 点胶囊 / 安装开始后 1.5s 自动展开 | 380×auto（最大 560 高），可拖动 | 时间轴 + 环境项 + 主按钮 |
| **遮罩**（sheet） | 需用户确认（执行命令 / 卸载残留） | 居中 480 宽 | 列出命令原文，勾选后确认 |

**为什么不是居中模态**：装插件时用户经常要跳走查资料（NapCat 怎么装、模型 key 在哪申请）。
居中模态挡住整个面板，逼用户先关掉再查，查完还得找回来。浮窗让"装"和"查"并行。

### 11.2 阶段时间轴

后端已有 `Task.Update(id, phase, progress, message)`，**`phase` 参数现在一直传空串**。
不改结构，只约定枚举值：

| phase | 显示 | 进度区间 |
|---|---|---|
| `download` | 下载插件包 | 0–15 |
| `extract` | 解压 | 15–20 |
| `validate` | 校验清单 | 20–25 |
| `precheck` | 环境预检 | 25–30 |
| `install` | 写入插件目录 | 30–40 |
| `env` | 准备环境 | 40–90 |
| `start` | 启动 | 90–97 |
| `verify` | 验证 | 97–100 |
| `done` / `failed` | 完成 / 失败 | — |

时间轴只在**经过或即将经过**的阶段显示，未到达的置灰但可见——让用户知道"还有几步"，
而不是盯着一个百分比猜。

```
● 下载      ✓ 2.3s
● 解压      ✓ 0.4s
● 预检      ⚠ 4 项待处理          ← 当前
○ 写入
○ 环境
○ 启动
```

### 17.2 与设计的三处偏差（都是实施中发现的）

**① 旧式 `requirements` 的 `fix` 用 `manual`，不是文档写的 `auto`**

文档 §6.4 写 `Fix:"auto"`。实施时发现这会打破一个不变量：
**`fix=auto` ⟺ 存在匹配的 `apply` 步骤**。旧式清单没有 `apply`，
标成 auto 会让前端渲染出一个点了没反应的「一键修复」按钮。
改为 `manual` + `hint` 给出可复制的 pip 命令。

**② 前端落点改成「列表行内展开」，不是「插件详情页签」**

文档 §11.13 说在插件详情加"环境"页签。实际 `/plugin/:name`（`PluginView.vue`）
渲染的是**插件自己的前端产物**，面板没有地方往里加页签。改成在已安装列表的行内展开，
离"看到哪个插件不对"更近，也不用改路由。

**③ 新增了文档没列的两个文件**：`euid_unix.go` / `euid_other.go`。
`os.Geteuid()` 在 Windows 上不存在，不加 build tag 会导致开发机编不过。

### 17.3 实施中修掉的真问题

**`CommandContext` 的超时是假的。** 只杀 `sh` 本身，它派生的子进程
（`sleep`、`xvfb-run` 之类）还活着并持有 stdout 管道，`Wait` 会一直等 IO 收尾。
实测 `sleep 5` + `timeout 1` 跑满 **5.13 秒**，超时形同虚设。
加 `cmd.WaitDelay = 500ms` 后降到 **1.53 秒**，测试断言收到 3 秒防回归。

> 这个坑对 `apply` 阶段更要命：`apt install` 超时后会挂到天荒地老。

### 18.2 安全边界（这套机制唯一会写系统的地方）

1. **前端只传步骤 id，不传命令原文**。传原文 = 任何登录用户都能在面板上执行任意 shell。
   命令永远来自插件清单，报告里把它原样带给前端看（`EnvReport.apply[].command`）。
2. `level=check` 的清单**拒绝执行**（不是降级，是拒绝）。
3. `needs=root` 的步骤在非 root 面板上**直接拒绝**——不 sudo、不降级、不"试试看"。
4. 必须 `confirm:true`，且确认页把命令**完整摊开**：不折叠、不省略、不搞"展开查看详情"。
   命令框横向滚动而不是折行——折行会让人读错命令。
5. 步骤失败即停（venv → pip → unit 这类有依赖顺序，后面跑了也是白跑）。
6. 幂等：步骤可用 `check` 字段关联检查项，已就绪就跳过——点第二次修复不会重复装一遍。

### 18.3 实施中发现的两个真问题

**① "读不到"被当成"缺失"——非 root 部署会永远显示"环境未就绪"**

QQBot 的 `runtime` 检查要比对 `/opt/rcbot` 里已部署的源码。那是 root 的 600 文件，
面板在 dev 上以 `f` 运行 → `cmp` 返回 2（权限不足）→ 检查判定"缺失"。
后果：非 root 部署永远报缺东西，把真正缺的那项盖掉。

修法有两条，缺一不可：
- **框架加退出码约定**：`1`=确定缺失、`2`=无法确定（unknown）、`3`=状态可疑（degraded）。
  读不到时命令 `exit 2`，报告就是 `unknown` 而不是 `missing`，且**不计入 pending**。
- **让被检查的文件可读**：apply 步骤安装源码后 `chmod 0644`。
  （只放开 `.py` 源码；含 API key 的 `data/config.json` 保持 600。）

**② 之前只探"NapCat 程序在跑"，没探"QQ 真的登录了"**

`napcat` 检查打的是 WebUI(6099)，程序活着就返回 200 → 判 ok。
但 QQ 掉线时 6099 照常响应，**机器人其实不回话**，报告却显示一切正常。

补了 `onebot` 检查：OneBot WS 端口 6700 **只有 QQ 登录后才监听**，
所以"6700 在监听"才是"机器人能不能回话"的真判据。
（实测：用户主动登出 QQ 后，6700 不在 → 报告如实报 `missing` + "需手动扫码"。）

### 18.5 P2 执行器六条路径（真机验证）

| # | 场景 | 结果 |
|---|---|---|
| ① | 初始报告 | `flag` missing / `fix=auto` / `apply_steps=['make']`；`exit 2` 的项为 unknown 且不阻断 |
| ② | 不带 confirm | 400「未确认」 |
| ③ | 执行 make | 200，步骤 ok（detail=created），报告刷新为 ready=true |
| ④ | 再执行一次 | skipped（幂等） |
| ⑤ | root 步骤 + 非 root 面板 | denied，`ok=false`，`denied=1` |
| ⑥ | 未知步骤 id | 400「步骤 "nope" 不在该插件的清单里」 |

### 18.6 QQBot 的环境声明（5 项检查 + 2 个步骤）

| 检查 | 判据 | 缺了怎么办 |
|---|---|---|
| `napcat` | WebUI(6099) 响应 2xx | 手动（第三方客户端，面板装不了） |
| `onebot` | OneBot(6700) 在监听 = QQ 已登录 | 手动扫码 |
| `deps` | venv 里能 import aiohttp/aiosqlite/PIL | **自动**（建 venv + pip install） |
| `runtime` | 已部署源码与插件包逐文件一致 **且** 服务在跑 | **自动**（同步源码 + 写 systemd unit + 重启） |
| `port6710` | 端口占用者是不是 rcbot 自己 | 结构化端口检查 |

两个 apply 步骤都 `needs: root`（要建 venv、要写 `/etc/systemd/system/`）。
插件包现在**自带 rcbot 运行时源码**（`deploy.py` 的 `PLUGIN_FILES` 加了 `rcbot.py` + `rcbot/*.py`），
否则用户装完插件还得另外找地方下载机器人本体，市场安装就断链了。

### 18.7 P3 还没做

市场安装（`core/store.go` 的 `InstallPlugin`）尚未接入预检与时间轴——
现在只有上传安装这一条链路有 `env`。市场安装要等 registry 里真正有 QQBot 条目再做。
