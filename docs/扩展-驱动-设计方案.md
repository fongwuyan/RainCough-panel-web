# 系统扩展「驱动」设计方案（v2，待确认）

> v1 的错误：把驱动逻辑写在面板 Go 里，等于每加一个扩展都要改面板二进制。
> v2 改成：**扩展包自带后端与接口**，安装即注册接口，卸载即注销；面板二进制只提供机制。
> 本文只写方案，确认后再动代码。

## 一、目标

- 面板里能看清"硬件 ↔ 驱动"对应关系，并安装/更换驱动，出问题能回滚。
- 顺带把扩展机制补成"自带接口"：以后写任何系统扩展都不需要改面板二进制。

## 二、现状体检（2026-10-01 实测，作为设计依据）

| 项 | 实测值 |
|---|---|
| 系统 / 内核 | Debian 12 (bookworm)，6.1.0-52-amd64，x86_64 |
| 显卡 / 网卡 / 存储 | Intel Iris 6100 → **i915 已绑定**；Realtek RTL8111 → **r8169 已绑定**；SATA AHCI → **ahci 已绑定** |
| USB | 只有 Intel/Terminus Hub，无 WiFi 网卡 |
| 固件 | firmware-linux-free / -misc-nonfree / -realtek 已装，`/lib/firmware` 99 项，dmesg 无加载失败 |
| DKMS / headers | **未装 dkms、未装 linux-headers**；build-essential + gcc 12 已装 |
| Secure Boot | **已关闭**（无需 MOK 签名） |
| apt 源 | 清华镜像，`main contrib non-free non-free-firmware` 齐全（firmware-iwlwifi 候选 20230210-5） |

结论：这台机器现在不缺驱动 → 驱动扩展的第一价值是**体检 + 缺什么装什么**，安装能力主要为将来服务
（插 WiFi 网卡、换网卡要 DKMS、加 NVIDIA 卡）。

## 三、机制部分（★先做这个，一次性）

### 现状与差距

| | 插件(plugin) | 系统扩展(extension) 现状 | 目标 |
|---|---|---|---|
| 清单 | `plugin.json` v4：含 `backend{lang,exec,capabilities}` + `interfaces[]` | `extension.json`：只有 name/label/version/desc/author/icon/entry/route | 扩展清单也支持 `backend` + `interfaces` |
| 端点 | pluginx 扫 `plugins/` 预建 `<name>.sock` | 不扫扩展目录 | pluginx 同时扫 `extensions/` |
| 进程 | 独立 systemd 单元（面板外管理） | 无后端概念 | 安装后由面板生成并启用 `rc-ext-<name>.service` |
| 接口 | 进程连上来注册进接口库 | 只能调面板内置接口 | 扩展注册自己的接口，前端用 `/api/interfaces/<id>/invoke` 调 |

### 要做的事（P0）

1. **清单**：`Extension` 结构体与校验增加
   `backend{lang, exec[], capabilities[]}` 与 `interfaces[]{id, visibility, version, description, input, output}`
   （与 `pluginx.ManifestV4` 同形，直接复用类型）。
2. **端点**：`pluginx.Options` 增加 `ExtDir`；`Start()`/`Reload()` 同时扫描 `extensions/`，
   对**声明了 backend** 的扩展预建端点并写 `<extdir>/.rc.endpoint`（与插件一致）。
3. **进程托管**：安装扩展时若清单有 backend →
   生成单元 `rc-ext-<name>.service`（`ExecStart=<exec>`、`WorkingDirectory=<扩展目录>`、
   `Restart=always`、`User=root`），`systemctl daemon-reload && enable --now`；
   卸载时 `disable --now` + 删单元 + 删目录。面板重启不影响后端（与插件同款）。
4. **接口可见性**：扩展页展示"本扩展提供的接口"（`/api/interfaces?plugin=<name>`：id / visibility /
   online / 调用次数 / 平均耗时），并提供「重启后端」按钮。
5. **安全**：单元文件由面板生成，命令只来自清单的 `exec` 字段（不接受任意 shell）；
   `interfaces` 的 `visibility=main` 表示仅面板可调（插件调不到）；
   卸载时先停进程再删目录，避免半死进程。

> P0 做完后：新增系统扩展 = 往 `extensions/` 放一个包（前端 + 可选后端 + 接口声明），
> 面板二进制不再需要改。**驱动扩展就是第一个按这套写的扩展。**

## 四、驱动扩展设计

包结构：

```
extensions/drivers/
  extension.json         # name=drivers label=驱动 version=1.0.0 icon=DV route=/ext/drivers
                         # backend{lang:python, exec:[python3, server.py]}
                         # interfaces[ drivers.overview / drivers.modules / ... ]
  frontend/extension.js  # 或 .vue，由 tools/build-extension.js 打包
  assets/extension.js    # 构建产物(面板托管)
  server.py              # 后端: 实现 drivers.* 接口(标准库 + subprocess, 零第三方依赖)
```

### 接口清单（后端提供）

| 接口 | visibility | 说明 |
|---|---|---|
| `drivers.overview` | all | 内核/headers/dkms/SecureBoot/apt 组件 + 设备表(设备·绑定驱动·模块版本·固件状态) + 问题清单 |
| `drivers.modules` | all | 已加载模块(lsmod)与 `modinfo` 搜索 |
| `drivers.module.action` | main | `load / unload / persist_on / persist_off / blacklist / unblacklist` |
| `drivers.packages` | all | 固件包 / DKMS 包候选与安装状态（apt-cache policy 解析） |
| `drivers.install` | main | `{kind: firmware\|dkms\|vendor, name, confirm}` → 预检 + 执行 |
| `drivers.rollback` | main | `{backup}` 恢复模块配置 |
| `drivers.log` | all | 动作历史（命令/输出/退出码/时间） |

### 页面（系统扩展 → 驱动，四段，文字为主、直角、无提示词）

1. **体检（只读）**：摘要行（内核 · 架构 · Secure Boot · DKMS · headers）；设备表；
   问题清单（未绑定驱动 → 给可加载模块名；固件缺失 → 由 dmesg 失败行映射到固件包；缺 dkms/headers → 一键准备）
2. **内核模块**：已加载列表（含"是否开机自动加载"）、搜索、加载/卸载/持久化/黑名单
3. **安装驱动**：固件包 / DKMS 驱动（先备 dkms+headers+build-essential）/ 厂商驱动（识别到 NVIDIA 才出现）；
   **每次先出预检**（将执行的命令、将装/替换的包、是否影响当前网络或显示、是否更新 initramfs、是否需重启），确认后才执行
4. **备份回滚 + 日志**：改动前打包 `/etc/modprobe.d`、`/etc/modules-load.d` 到
   `<APP_DIR>/data/driver-backup-<时间戳>.tar.gz`；可一键恢复；日志可复制

## 五、安全护栏

1. **不静默动网卡/显卡**：卸载在用的网络/显示驱动必须显式勾选确认，并写明后果（会断网/会黑屏）。
2. **改动前必备份**，备份失败不执行。
3. **不自动重启**：需要重启的动作只标记"待重启"，由你点。
4. **命令白名单**：只跑固定模板（modprobe/modinfo/dkms/apt-get install 指定包/update-initramfs），不接受任意 shell。
5. **apt 不改源、不加第三方仓库**；缺 `non-free-firmware` 只提示。
6. **每步留痕**：命令、输出、退出码、时间、执行者。
7. 后端以 root 运行是驱动操作的前提 → 面板**不把 sudo 密码交给扩展**，扩展自己就是特权进程，
   权限边界写在 `visibility=main` 上（敏感接口插件调不到）。

## 六、分阶段

| 阶段 | 内容 | 说明 |
|---|---|---|
| **P0** | 扩展自带接口机制（清单 + 端点 + 单元托管 + 接口展示 + 卸载注销） | 一次性投入；用一个最小样板扩展验证注册/注销后再写驱动 |
| **P1** | 驱动扩展：体检（只读） | 零风险，先能用起来 |
| **P2** | 驱动扩展：模块管理 + 备份回滚 | 有护栏，可能断网 |
| **P3** | 驱动扩展：固件/DKMS/厂商驱动安装 + 预检 + 日志 | 要真装包，单独一轮验证 |
| **P4** | 可选：第三方封装(.run/tar.gz)上传 DKMS 构建、apt 组件检查与开启 | 按需 |

## 七、需要你定的几件事

1. **P0 先单独做一轮**（推荐，含一个最小样板扩展做验证），还是 P0+P1 一起做？
2. **后端语言**：Python（与插件一致、零编译、现成运行环境）还是 Go（编译成单文件、无运行时依赖）？我建议 Python。
3. **后端托管**：systemd 单元 `rc-ext-<name>.service`（与插件一致，面板重启不影响）——同意吗？
4. **危险动作**：默认禁止卸载"正在使用"的模块（需勾选确认）——够严吗？
5. **安装范围**：只允许固件包 + DKMS 包 + 官方厂商驱动包，还是也允许手填任意包名？
6. 版本口径：扩展自身 `version` 写 `1.0.0`；面板 VERSION 仍 `1.0.0`（P0 会改二进制，资产重发一次）。
